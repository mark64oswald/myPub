Data products and industry models in myPub

Tonight added two things to the knowledge base. The first is the Open Data Product standards, which say how to package, contract and govern data. The second is the Databricks industry data models plus the reference models around them, which give the raw material to model data in the first place. A set of generators now carries a design from one to the other, grading it against your books along the way.

Why

myPub's books already explain data products, data mesh and data modeling patterns well. What the knowledge base lacked was a way to turn that understanding into artifacts that a machine can check. There are two halves to that problem.

How to describe and deliver a data product

Books say a data product needs an owner, a contract, SLAs, quality rules and a reason to exist. The Open Data Product standards turn each of those into a YAML field with a JSON Schema and an SDK that validates it. Loading the specs lets myPub answer "where does this go in ODPS?" and lets generators write files that pass the validator, not prose that only describes them.

What data the product is made of

A product is only as good as the model under it. Silverston, Hay and Fowler teach patterns such as Party/Role, contact mechanisms and status history. The Databricks gallery offers 41 industries of ready-made tables, mostly LLM-generated. Putting both in the catalog lets myPub grade a model against the patterns, rewrite it, and cite the page that justifies each change.

The aim is a chain where each step is grounded in the library and checked by a machine: a business description becomes a pattern-first model, the model becomes contracted tables, and the tables become products in a governed portfolio.

What was built

A Open Data Product standards

The family is five Linux Foundation specifications plus an SDK. ODPS 4.2 describes one product, ODPC 1.0 is the portfolio, ODPG 1.0 is the value graph, ODPV 1.1 is the shared vocabulary, and ODPR 1.0 (draft) is the recipes for building them. ODCS v3.1.0 from the Bitol project supplies the data contract that ODPS points to. It came in three layers.

The Databricks models fail in the same ways in every industry. Person identity is copied onto every role table, addresses sit inline on 10 to 43 tables, the insurance-heavy ECMs model coverage 10 to 15 times, and 40 to 60% of foreign keys are labeled "LLM Generated Cross-Domain Link". The grades describe Databricks' models. The grader was not loosened to raise them. Two false positives were fixed instead (#56 coverage evidence, #57 status-history tables).

The Databricks License covers the gallery, so model content stays in the local catalog and in data/generated-packages/. This review quotes grades and counts only.

How it fits into the knowledge base

Each new piece lands in one of the three stores myPub already had, or in the new one. The spec text goes to doc sections, the spec relationships to the concept graph, and the models to the reference-model tables. The generators read across all of them, and every output they write is checked by a machine: the ODP SDK, the ODCS JSON Schema, or the pattern grader.

How the two workstreams connect

The two workstreams cover the two halves of one path. The model generators make sure the tables are sound, and the ODP generators make sure the product built on them is described, contracted and governed. /kb-dp-from-model joins them. It takes a slice of tables and writes one ODCS contract per table, ODPS KPIs taken from the model's metric views, and Unity Catalog DDL. Then /kb-dp-portfolio builds the catalog, graph and recipe around them.

Three smaller links connect the halves too.

  • Shared vocabulary. /kb-dp-from-model uses ODPV terms (UseCase, BusinessObjective, KPI, governedBy) for the graph it builds from a model, so the ODP review step reads it like any other portfolio.
  • Review notes travel with the product. Each product package carries a model-notes.md that lists the model-review findings touching its tables, so a contract reviewer sees, for example, that coverage was held in three places.
  • Synthetic data. The sample-data/healthsim-request.md file asks HealthSim for rows in foreign-key order. That closes the loop from model to something you can load and query.

Worked examples

These start simple and build up. Examples 1 to 4 show results from runs tonight. Example 5 is a recommended next run that has not been executed yet.

Example 1 · ask in natural language · done tonight

Search the specs

No slash command is needed. Ask Claude in any project with the plugin installed, and the question routes to the mypub-kb tools.

# "How do I define an SLA in ODPS 4.2?"
search_chapters("how do I define an SLA in ODPS", mode="interactive")
#  primary:        ODPS 4.2 spec, SLA component (declared dimensions + SLA-as-code)
#  corroborations: ODCS slaProperties page; Building Data Products chapter (Bitol ODPS)

# "What do I need to understand before ODPR?"
find_prerequisites("Open Data Product Recipe Specification", max_depth=2)
#  depth 1: ODPS, ODPC, ODPG          depth 2: ODPV terms ... 75 concepts in all

# "How do my authors treat ODPS?"
compare_concept_across_authors("ODPS 4.2")
#  now includes Moilanen, Data Product Portfolios (missing before the concept merge)

Two tips. Say "ODPS 4.2" when you mean the Linux Foundation spec, because a bare "ODPS" still resolves to Bitol's standard. Keep max_depth at 2 for the specs. At depth 5 the walk runs through general ideas like Data Product and passes 3,000 nodes.

Example 2 · one table · runs in seconds

Write a contract for a table you already have

Give /kb-data-contract a table and its DDL. It writes an ODCS v3.1.0 contract and checks it against the ODCS JSON Schema. Primary keys get uniqueness rules, required columns get not-null rules, and personal columns are marked restricted. The judgement calls, such as owner, purpose and SLA values, stay as TODOs for a person.

/mypub:kb-data-contract member_eligibility --ddl ddl/member_eligibility.sql \
    --platform databricks --location vbc.silver.member_eligibility
# member_eligibility.odcs.yaml (trimmed)
apiVersion: v3.1.0
kind: DataContract
id: member-eligibility
version: 0.1.0
status: draft
description:
  purpose: "TODO: why member_eligibility exists."
schema:
  - name: member_eligibility
    physicalType: table
    properties:
      - name: member_id
        logicalType: string
        primaryKey: true
      - name: birth_date
        logicalType: date
        classification: restricted
    quality:
      - name: table_not_empty
        metric: rowCount
        mustBeGreaterThan: 0
      - name: member_id_unique
        metric: duplicateValues
        mustBe: 0
slaProperties:
  - { property: availability, value: 99.5, unit: percent }
  - { property: frequency,    value: 1,    unit: d }
  - { property: latency,      value: 4,    unit: h }
Example 3 · whole model · done tonight

Review a model, then improve it

Point /kb-model-review at any model: a Databricks model.json, plain DDL, or one already in the catalog.

/mypub:kb-model-review databricks:healthcare           # gallery MVM → grade D
/mypub:kb-model-review ref:48                          # healthcare ECM → D (57%)
/mypub:kb-model-review ~/work/claims/ddl.sql           # your own DDL

Each finding names a pattern, cites its books, and ends with a vibe, a change request you can paste into Databricks' Vibe Data Modeling agent. If you'd rather myPub do the rewrite, run /kb-domain-model. For a "community hospital revenue cycle" over the healthcare model, it kept 54 tables and added the party, contact-mechanism and status-history tables, 93 tables in all. The grade went from D to B, with this section profile:

The subagent refinement pass handles the classification tables and the cycles. That's how the five ECM rewrites reached A and B. Judging the generated foreign keys needs source-system knowledge, so that part is left to you.

Example 4 · SQL over the reference-model layer · read-only

Ask the models a pattern question

The ref_* tables have no MCP tool yet, but they answer cross-model questions well in SQL. Run these on an APFS clone (cp -c data/catalog.ddb /tmp/ro.ddb), because the catalog allows one writer. First: which entities from any source play the Party Role pattern, and how sure is the link?

SELECT m.source,
       m.industry,
       m.flavour,
       e.domain,
       e.name        AS entity,
       c.confidence,
       c.method                         -- heuristic or subagent
FROM   ref_entity_concept AS c
JOIN   ref_entity         AS e ON e.ref_entity_id = c.ref_entity_id
JOIN   ref_model          AS m ON m.ref_model_id  = e.ref_model_id
WHERE  c.pattern_key = 'party_role'
  AND  m.industry IN ('healthcare', 'health_insurance', 'insurance')
ORDER  BY m.source, c.confidence DESC;

Next, a rollup that makes the "coverage modeled 10 to 15 times" finding visible, with Silverston and the pattern-first rewrites side by side.

SELECT m.name AS model,
       count(DISTINCT e.ref_entity_id)
           FILTER (WHERE c.pattern_key = 'coverage')   AS coverage_entities,
       count(DISTINCT e.ref_entity_id)
           FILTER (WHERE c.pattern_key = 'party_role') AS role_entities
FROM   ref_entity_concept AS c
JOIN   ref_entity         AS e ON e.ref_entity_id = c.ref_entity_id
JOIN   ref_model          AS m ON m.ref_model_id  = e.ref_model_id
WHERE  c.confidence >= 0.5
  AND  m.industry IN ('healthcare', 'health_insurance', 'insurance')
GROUP  BY m.name
ORDER  BY coverage_entities DESC;
Example 5 · end to end · recommended next run

A value-based care data product, from model to portfolio

This fits your Vantage work and uses every new piece. The built-in healthcare example (Encounter activity, Claims and denials, Patient coverage) already ran the second half of this path, and all its contracts, products, catalog, graph and recipe pass the SDK. This run would add the pattern-first first half and a value-based care scope.

  1. Frame it. Search before generating: "attribution and shared savings in value-based care" and "how ODPC models use cases and business objectives". The first pulls book chapters, the second the ODPC spec. Together they tell you which products and KPIs to ask for.
  2. Build the model. Start from the pattern-first health insurance ECM, which already passes Party/Role and has one coverage owner. 
    /mypub:kb-domain-model "Value-based care: member attribution to PCPs, care gaps
    from quality measures, total cost of care, shared-savings reconciliation"
    --base ref:<pattern-first health_insurance id>
    If the description needs tables the base lacks, such as a quality-measure result, the command sends an Agent to add them and records each addition in changes.md with the book it relies on. The review should stay at A or B.
  3. Slice it into products. 
    /mypub:kb-dp-from-model <model.json from step 2> \
    "Member attribution: members and PCP attribution periods => domain:attribution" \
    "Care gaps: quality-measure results and open gaps => domain:quality" \
    "Total cost of care: allowed amounts by member month => domain:claim" \
    --catalog vbc
# then, when Claude asks for use cases and objectives:
#   "Shared-savings reconciliation: settle the contract year => Member attribution, Total cost of care"
#   "Care-gap outreach: close open gaps before year end => Care gaps, Member attribution"
#   "Earn shared savings: beat the cost benchmark on quality => Shared-savings reconciliation"

    The domain names depend on what step 2 produces, so check model.json first and name its tables or domains.

    You get one ODCS contract per table, ODPS products whose KPIs come from the metric views (PMPM cost, gap-closure rate, with targets left as TODO), Unity Catalog DDL for vbc.*, an ODPC catalog, an ODPG graph in which each product supports a use case and is governedBy its contract, and a HealthSim request for MemberSim rows.
  4. Grade and hand off. /kb-dp-review products/total-cost-of-care.odps.yaml --contract … --graph … grades each section A–F against the specs and Data Product Portfolios. Then /kb-dp-recipe writes the ci recipe (validate on every change) and the agent recipe (the build brief for whoever writes the pipelines).
  5. Check. Run make all in the package. It runs open-data-products validate, odpc-build, odpg-analyze and a recipe dry run.

Since the base is a derivative of a Databricks model, the package stays in the local data/generated-packages/, like the other model outputs.

Example 6 · greenfield · no model needed

Start a product from an idea

Without a source model, /kb-bootstrap with the data-product profile writes the spec files instead of code. It detects the profile from the request.

/mypub:kb-bootstrap "customer churn data product on Databricks"
# → ODPS product, ODCS contract, ODPC use case + objective fragments,
#   ODPG value graph, ODPR recipe, Makefile        (make all → SDK passes)

Use /kb-dp-portfolio instead when you have several products in mind at once.

Open items and next steps

A Data product specs

  • SDK 0.7.0 gaps. The SDK checker and the 4.2 schema disagree on dataHolder, so generated products leave it out. The SDK can't validate a DataProductRecipe or ODPV value tracking yet, and odpg-build needs a local Ollama. Re-check each of these when the SDK releases a new version.
  • Generator quality on real work. All four generators pass the SDK, but none has been graded on a real portfolio. The recipe build plan still pulls one off-topic Palantir procedure.
  • Possible extra sources. The 14 YAML examples in the knowledge-base repo, the remaining ODCS pages (team, roles, servers, pricing) and the ODPV mapping profiles (DCAT-3, ODRL, PROV-O, OpenLineage) were listed as worth adding. They weren't in the second-layer load.
  • Naming. A bare "ODPS" resolves to Bitol's standard. That's deliberate, but worth knowing when a search looks wrong.

B Industry models

  • Review the five pattern-first models. They are drafts until you've read one. Healthcare (A) or health insurance (B) is the best place to start, given the value-based care work.
  • LLM-generated foreign keys. About 40% remain in every rewrite. Pruning them needs source-system knowledge, and this is the main thing keeping three models at B. Double-owned concepts are the other: payer and NDC in pharma, offering in insurance.
  • Fairer reference coverage. Coverage matches on names, so SDTM coverage reads 38–46% even where tables like trial_dosing plainly cover EX. Matching on entity embeddings and pattern links would fix it. That changes the coverage numbers more than the letter grades.
  • The other 36 MVMs have heuristic pattern links only, with no subagent pass. Map any of them on demand.
  • A ref_* query tool. Example 4 shows these questions are useful. An MCP tool such as find_pattern_implementations(pattern, industry) would make them natural-language questions.
  • Regenerate the revenue-cycle sample. The saved hospital revenue cycle review predates PR #57 and still shows status-history tables asked for their own history.

Both

  • Run Example 5. It is the first test of the whole path on a problem you care about, and it would show where each half is weakest.
  • Housekeeping. Five catalog_pre-odp-* backups from tonight are still in data/ on the Mac. They are APFS clones, so they cost little until the catalog changes a lot.
